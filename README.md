# Vax-Dealers — Agentic AI для прогнозирования ВЭС

Рабочий прототип для кейса Самрук-Казына HackAlem AI. Прогнозирует среднюю нормализованную активную мощность двух турбин по часам на 48 часов и воспроизводит ежедневные расчёты с 31 января по 28 февраля 2026 года.

## Готовые результаты

Готовые CSV скачиваются одним файлом: [forecast_results.zip](results/forecast_results.zip). Распакуйте его в корень проекта: архив содержит папку `results/` с файлами ниже. После локального `replay` те же CSV создаются автоматически.

- `results/submission_february.csv` — 1 344 записи: 672 часа февраля × 2 турбины, один прогноз на следующие сутки на каждый час.
- `results/forecasts_48h.csv` — 2 784 записи: 29 ежедневных выпусков × 48 часов × 2 турбины. Выпуски в конце месяца продолжаются в марте.
- `results/station_february.csv` — обе турбины рядом и условное среднее при равной номинальной мощности.
- `reports/january_metrics.csv` — независимая проверка точечного прогноза на январе.
- `reports/data_audit.json` — аудит исходных CSV.
- `reports/model_card.json` — параметры модели, признаки, разделение данных и калибровка неопределённости.

Для каждого горизонта метрики считаются по выпускам прогноза; пересекающиеся горизонты не суммируются как выработка.

## Запуск

Python 3.12. Команды выполняются из корня репозитория.

```bash
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# Linux/macOS вместо предыдущей команды: source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Положите два исходных CSV организаторов в папку `raw/`. Сохраните окончания имён `turbine 1.csv` и `turbine 2.csv`. Исходные CSV, обученная бинарная модель и погодный кэш не нужны для просмотра готовых прогнозов; для полного пересчёта выполните:

```bash
python wind_agent.py prepare --data-dir raw
python wind_agent.py fetch
python wind_agent.py train
python wind_agent.py replay
```

`fetch` автоматически скачивает месячные блоки архивных прогнозов для обеих координат, повторяет неудачные запросы и сохраняет кэш. Нужен интернет, API-ключ не требуется. Соблюдайте ограничения бесплатного API. После первой загрузки `train` и `replay` работают без сети. Установка зависимостей и загрузка архива зависят от доступности внешних сервисов.

Один исторический выпуск с повторной загрузкой погоды:

```bash
python wind_agent.py replay --first-issue 2026-02-10 --last-issue 2026-02-10 --refresh
```

Мониторинг обновлений для выбранного исторического выпуска:

```bash
python wind_agent.py watch --issue-date 2026-02-10 --interval-seconds 3600
```

`watch` — явный локальный процесс, остановка Ctrl+C. Он регулярно получает данные и повторяет расчёт; fingerprint в журнале позволяет определить изменение входов. Это режим воспроизведения архива, не подключение к действующей SCADA. Полный `replay` записывает результаты в `results/`, отдельный выпуск — в `results/cycles/<дата>/`.

## Агент и модель

Агент реализован как детерминированный контроллер с ML-моделью и инструментами: PLAN → FETCH → VALIDATE → PREDICT → REVIEW → PUBLISH. Он сам выбирает давность погодного прогноза по горизонту, загружает и проверяет данные, запускает модель, отмечает скачки мощности и публикует результат. При недоступности сети использует сохранённый кэш; при отсутствии или некорректности погодных значений переходит на историческое среднее с явным статусом `fallback_climatology` и диапазоном [0,1]. Журнал `results/agent_events.jsonl` содержит решения и отпечатки входов. В полном февральском расчёте резервная модель не понадобилась.

Это ограниченный агент на правилах, без LLM и без заявления о свободном планировании. Такая архитектура делает повторяемыми решения, связанные с доступностью данных. Дальнейшее развитие: LLM для объяснения аномалий через контролируемые инструменты и независимый журнал действий, без права менять прогнозные числа.

Модель — `HistGradientBoostingRegressor`. Признаки: прогноз ветра на 80 м, температура 2 м, синус/косинус направления, часа и месяца, давность прогноза и идентификатор турбины. Высота ступицы неизвестна; 80 м — признак погодной модели, а не установленная высота турбины. Фактическая скорость ветра из будущих SCADA-записей не используется для прогнозирования.

Разделение по времени:

1. Архив погоды с апреля 2024 года, обучение кандидатов до конца ноября 2025.
2. Декабрь 2025 — выбор одного из трёх заранее заданных наборов параметров.
3. Финальная модель обучается по 31 декабря 2025; январь исключён из обучения точечного прогноза.
4. Январь 2026 — проверка точечного прогноза и калибровка радиусов интервалов. Для калибровки берутся только часы, завершившиеся к первому выпуску 31 января 23:00 местного времени.
5. Февраль — последовательные ежедневные прогнозы; модель зафиксирована, внешние прогнозные признаки обновляются. Переобучение не требуется для ежедневного обновления расчёта.

`lower90`/`upper90` построены по 90-му процентилю абсолютных январских ошибок отдельно для турбины и горизонта суток. Это эмпирический диапазон: гарантии 90% покрытия при временной зависимости и смене погоды нет. Январь используется для калибровки интервалов, поэтому он не является независимым тестом их покрытия.

## Погодный архив и защита от будущих данных

Источник: [Open-Meteo Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api), модель `gfs_seamless` (NOAA GFS). В запросах явно указаны `wind_speed_unit=ms` и `timezone=GMT`. Данные Open-Meteo: CC BY 4.0, с атрибуцией Open-Meteo и NOAA; условия сервиса проверяйте перед коммерческим использованием.

Используются прогнозные ряды `previous_day1`, `previous_day2`, `previous_day3`. Реанализ и фактическая погода не подставляются вместо прогнозов. Для горизонта h выбирается `d = ceil((h + 12)/24)`:

| Горизонт | Давность ряда |
|---|---|
| 1–12 ч | previous_day1 |
| 13–36 ч | previous_day2 |
| 37–48 ч | previous_day3 |

Проверка: `valid_time − d × 24 ч + 12 ч ≤ issue_time`. Запас 12 часов принят на вычисление и публикацию прогноза. `availability_bound_utc` — расчётная граница по этому допущению, **не фактическая отметка публикации**. API фиксированных давностей не отдаёт точный ID выпуска и публикационное время; один 48-часовой прогноз может использовать несколько погодных выпусков.

Поэтому строгая доказуемость «именно этот файл был опубликован к моменту расчёта» остаётся ограничением прототипа. Для строгого аудита нужно заменить адаптер на архив исходных выпусков GFS с временем инициализации и подтверждённой доступностью каждого файла. Использование точного времени инициализации само по себе тоже не доказывает время публикации. [Описание различий архивов](https://open-meteo.com/en/docs/historical-forecast-api).

В кэше сохраняются URL, время скачивания и SHA-256 ответа. Время скачивания в 2026 году не выдаётся за историческое время доступности. JSON манифест связывает погодные запросы с данным расчётом.

## Исходные данные и допущения

- Турбина 1: 43.645150, 78.535604 — [ссылка организаторов](https://maps.app.goo.gl/iN6svMt69D5qRpFU9).
- Турбина 2: 43.643198, 78.538828 — [ссылка организаторов](https://maps.app.goo.gl/8UQMwsYavY6nLvFY8).
- CSV содержат 142 360 и 149 499 десятиминутных записей. Оба заканчиваются **31.01.2026 23:50**, несмотря на февраль в названии. Фактических февральских значений нет, метрика февраля не заявляется.
- За общий период отсутствуют 9 992 и 2 853 десятиминутных слота. В модель допускаются только часы с 6 корректными измерениями; неполные часы не заполняются нулями и не интерполируются. Дубликаты временных меток вызывают ошибку.
- Метка CSV считается началом десятиминутного интервала. Часовой таргет — среднее шести значений. Семантика меток и часовой пояс не подтверждены организаторами.
- Принят UTC+5. Обучение с погодой начинается в апреле 2024, после изменения гражданского времени Казахстана. Для более ранних данных рассчитываются только статистики самой SCADA, без совмещения с погодой. При другом часовом поясе необходимо изменить `OFFSET` и полностью повторить обучение и прогнозирование.
- Выпуск ежедневно в 23:00 местного времени (18:00 UTC). Прогноз начинается в 00:00 следующих суток. Первый выпуск — 31 января; дополнительный выпуск 28 февраля охватывает март и сохранён отдельно в общей таблице.
- Номинальная мощность и признаки ремонтов/ограничений неизвестны. Результат — нормализованная средняя мощность, а не МВт·ч. При известных мощностях C1,C2: энергия станции за час = p1×C1×1ч + p2×C2×1ч. Поле `equal_capacity_mean_assumption` корректно как нормализованная мощность станции только при C1=C2.

## Что улучшать дальше

Подтвердить часовой пояс и смысл временных меток, подключить архив отдельных выпусков с журналом доступности, добавить высоту ступицы и номинальные мощности, учитывать ограничения/ремонты, сравнить несколько NWP-моделей на временной валидации. Для промышленного применения нужны новая независимая проверка, мониторинг смещения и оценка экономической стоимости ошибок.

## Проверки

`python -m unittest discover -s tests -v` проверяет временные границы всех горизонтов, покрытие февраля без дубликатов, обработку неполных часов, отказ на дубликатах SCADA, независимость признаков от фактической мощности и сохранение пропусков погоды для резервного режима. Численные результаты запуска и контрольные суммы сохранены в `reports/` и `results/`.
